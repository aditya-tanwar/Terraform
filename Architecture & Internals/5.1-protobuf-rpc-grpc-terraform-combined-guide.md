## A simple explanation with examples and the Terraform provider connection

These three terms are closely related, but they solve **three different
problems**:

-   **Protocol Buffers (Protobuf)** describes and encodes the data being
    exchanged.
-   **RPC (Remote Procedure Call)** describes the idea of calling an
    operation in another process or service.
-   **gRPC** is a framework that implements RPC communication. It
    commonly uses Protobuf for service and message definitions and
    HTTP/2 for transport.

The distinction is especially useful when learning how Terraform Core
communicates with provider plugins.

------------------------------------------------------------------------

## 1. Protocol Buffers (Protobuf)

**What it is:** A data serialization format and schema language.

Protocol Buffers, commonly called Protobuf, were developed by Google.
They let applications define structured data and serialize it into a
compact binary format.

Think of Protobuf as an alternative to sending data as JSON text.

### Example: the data we want to send

Imagine an application needs to send this information:

```json
{
  "name": "ec2-instance",
  "instance_type": "t2.small",
  "region": "ap-south-1"
}
```

With Protobuf, you first define the structure in a `.proto` file:

``` protobuf
syntax = "proto3";

message EC2Instance {
  string name = 1;
  string instance_type = 2;
  string region = 3;
}
```

This schema says that an `EC2Instance` message contains three string
fields. The numbers (`1`, `2`, and `3`) are field identifiers used in
the encoded format.

A program can then serialize an instance of this message into Protobuf's
compact binary representation and another program can deserialize it.

### Why use Protobuf?

-   Compact data representation.
-   Efficient serialization and deserialization.
-   Clearly defined message schemas.
-   Support for multiple programming languages.

**Remember:** Protobuf answers, *"What does the data look like, and how
is it encoded?"*

------------------------------------------------------------------------

## 2. RPC (Remote Procedure Call)

**What it is:** A communication pattern.

RPC allows one program to call a function or operation exposed by
another program. The other program may be running in a separate process
or on another machine.

Imagine two applications:

-   Application A: Terraform Core
-   Application B: AWS Provider

Terraform Core needs the provider to read information about an EC2
instance.

Conceptually, Core makes a call like this:

``` python
aws_provider.read_ec2_instance(
    instance_id="i-123456789"
)
```

The provider receives the request, performs the operation, and returns
the result.

Terraform Core does not need to implement the AWS API call itself. It
asks the provider to do the provider-specific work.

RPC describes the **remote-calling pattern**. By itself, RPC does not
prescribe one particular data format or network transport. Different RPC
systems can use different serialization formats and transports.

**Remember:** RPC answers, *"How can one program ask another program to
perform an operation?"*

------------------------------------------------------------------------

## 3. gRPC

**What it is:** An RPC framework.

gRPC is a high-performance framework for building communication between
services. It commonly combines:

-   **RPC:** The remote-calling model.
-   **Protocol Buffers:** Used to define service contracts and encode
    messages.
-   **HTTP/2:** Commonly used as the network transport.

### Example: defining a gRPC service

A `.proto` file can define both the message structures and the service
methods:

``` protobuf
syntax = "proto3";

service EC2Service {
  rpc GetInstance (InstanceRequest)
      returns (InstanceResponse);
}

message InstanceRequest {
  string instance_id = 1;
}

message InstanceResponse {
  string instance_type = 1;
  string region = 2;
}
```

This defines:

-   A service called `EC2Service`.
-   A remote operation called `GetInstance`.
-   The request message: `InstanceRequest`.
-   The response message: `InstanceResponse`.

The gRPC tooling can generate client and server code from this service
definition. The client uses that code to make a remote call; the server
implements the operation and returns a response.

**Remember:** gRPC answers, *"What framework can I use to implement
remote calls between services?"*

## 4. How the three fit together

Suppose a client application wants a server to retrieve a user's
details.

```text
Client application
       |
       | Calls a remote operation (RPC)
       v
   gRPC framework
       |
       | Sends the request over the network
       | commonly using HTTP/2
       |
       | Encodes/decodes message data
       | commonly using Protobuf
       v
Server application
       |
       | Executes the requested operation
       v
Response is sent back to the client
```

In the `.proto` example:

-   `message` defines the data structure --- **Protobuf**.
-   `rpc GetUser(...)` declares a remote method --- **RPC service
    definition**.
-   The gRPC framework uses the service and message definitions to
    support the client/server communication --- **gRPC**.

### Easy analogy

Imagine you need to ask someone in another country to do a task for you:

-   **Protobuf = the format of the message.** It defines how the
    information is arranged so the receiver can interpret it.
-   **RPC = making the remote request.** You ask someone elsewhere to
    perform an operation.
-   **gRPC = the communication framework.** It supplies the machinery
    and rules that make the remote request and response work.

The analogy is not exact, but it helps separate their responsibilities.

## 6. How this relates to Terraform

This is where the concepts become practical.

When you run:

```bash
terraform apply
```

Terraform Core needs to communicate with the AWS provider plugin so the
provider can perform operations such as reading, creating, updating, or
deleting AWS resources.

### The communication flow

```text
Terraform Core
      |
      | Terraform Plugin Protocol
      | RPC-based request/response communication
      v
AWS Provider Plugin
      |
      | AWS SDK call over HTTPS
      v
AWS EC2 API
      |
      | EC2 instance information / API response
      v
AWS Provider Plugin
      |
      | Response through the plugin protocol
      v
Terraform Core
```

There are **two separate communication paths**:

### Path 1: Terraform Core → AWS Provider

-   Terraform uses the **Terraform Plugin Protocol** to communicate with
    the provider plugin.
-   The communication is RPC-based.
-   The protocol defines how Core and the provider exchange requests and
    responses.
-   Modern Terraform provider protocols are gRPC-based and use defined
    protocol schemas.

### Path 2: AWS Provider → AWS

-   The provider uses the **AWS SDK**.
-   The SDK makes requests to AWS service APIs, typically over HTTPS.
-   For example, to retrieve EC2 instance details, the provider can call
    the EC2 `DescribeInstances` API.

### Important technical nuance

Terraform's provider communication uses its own versioned plugin
protocol and has specific protocol details. It is useful to understand
the RPC and gRPC concepts behind the architecture, but do not assume
every provider interaction is simply a generic gRPC call with an
arbitrary Protobuf schema. The exact details depend on the Terraform
Plugin Protocol version.

Also, **Protobuf is not the same thing as RPC**, and **RPC is not the
same thing as gRPC**. They describe different layers or
responsibilities.

## 7. Interview-ready answer

**Question: What is the difference between Protocol Buffers, RPC, and
gRPC?**

Protocol Buffers is a language-neutral serialization format used to
define and encode structured messages. RPC, or Remote Procedure Call, is
a communication pattern that allows one application to invoke an
operation in another application, potentially across a network. gRPC is
an RPC framework that commonly uses Protocol Buffers for service
definitions and message serialization, with HTTP/2 as its transport.

In Terraform, Core communicates with provider plugins through the
Terraform Plugin Protocol, which is RPC-based. The provider then uses
the relevant cloud SDK to communicate with cloud APIs, typically over
HTTPS.

------------------------------------------------------------------------

## 8. Final takeaway

Think of three separate questions:

1.  **Protobuf:** What does the message look like?
2.  **RPC:** How do I ask another program to perform an operation?
3.  **gRPC:** What framework can I use to make that remote call happen?

That is the core difference. Once you separate **data format**,
**communication pattern**, and **communication framework**, the
relationship becomes much easier to understand.
